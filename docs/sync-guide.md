# 浏览器同步与另一台设备拉取

LocalOTP 使用真实的 `chrome.storage.sync` 接口。开启浏览器账号同步后，Edge 由微软账号的同步服务传输，Chrome 由 Google 账号的同步服务传输。扩展没有自建云端服务，也没有用假数据模拟同步。

但**写入同步存储成功不等于已经上传到云端，或另一台设备已经收到**。浏览器未登录、关闭自身同步或离线时，同步存储可能仅在本机工作。浏览器决定网络传输时间，插件不能强制立即从服务器下载，也不能可靠判断用户是否登录云端账号。

## 两端操作

1. **源浏览器**：确认浏览器个人资料已登录，浏览器自身同步已开启；进入 LocalOTP“设置 → 同步与备份”，开启“浏览器同步”，点击“立即同步”。
2. **目标浏览器**：使用同一种浏览器登录同一账号，开启浏览器同步，安装相同扩展 ID 的 LocalOTP。首次打开先设置该设备自己的管理密码。
3. **目标插件**：同样开启“浏览器同步”，点击“立即同步”。浏览器已经送达的远端记录会与本地账号、分类及删除记录合并；之后远端变更到达会由后台自动合并。

“立即同步”会读取当前浏览器的同步存储副本，合并后写回本地和同步存储。因此可以同时拉取和推送；不需要另设一个“云端下载”按钮。

## 没有收到时

**旧的无 key 解压版首次切换到固定 ID 版时，要先导出备份，再加载新版并导入。不要先卸载旧版。** 本次 1.6.1 Release 已包含固定公钥，Windows Edge 与 macOS Edge 的 ID 均应为 `mjpifhendkddjgmoheglnfciammaipji`。后续保留该 key 更新即可，加载目录不再决定 ID。

“同步诊断 → 只读检查”显示实际运行的扩展 ID、本机和当前 ID 的同步缓存条数。当前源码还显示运行时版本与浏览器传输检查说明。缓存为 0 时不能证明旧账号从未存在，也不能证明云端永久丢失；先核对运行时 ID，ID 一致后应检查浏览器传输。原 1.5.0 同步键布局与本版兼容，同一 ID 不需要格式迁移。

- **Edge ↔ Chrome 不互通**：两个浏览器使用不同账号体系。Windows Edge ↔ macOS Edge 可以使用同一微软账号；Chrome ↔ Chrome 使用同一 Google 账号。
- 核对两端扩展 ID。设置中的“另一台浏览器如何拉取？”显示本机 ID，也可在扩展管理页面查看。未包含本次固定 key 的旧包仍可能按路径生成 ID，请确保两端都使用本次 Release。
- 不同 ID 时，可以先用“导出备份 / 导入备份”迁移。本次固定的是 GitHub ZIP 解压加载的身份，没有发布到扩展商店，也不会自动替换用户当前安装或迁移数据。
- 检查浏览器是否在线、同步是否暂停，插件是否显示容量或写入错误。同步上限约为 100 KB、每条 8 KB、512 条记录（含分类与删除记录）。
- 页面中的“同步完成”证明本地合并及 API 操作成功，不是两台设备云端传输的回执。

## 两端 ID 一致、A 有账号而 B 缓存为零

1. 在实际用于测试的浏览器个人资料中打开 `edge://sync-internals`，Chrome 使用 `chrome://sync-internals`。在 About 页记录 `Transport State`、`Disable Reasons`、`Auth Error`。
2. 查看 Type Info 中的 **Extension settings**（扩展设置），不是 **Extensions**（扩展安装列表）。这两类数据独立，后者正常不能证明账号数据已传输。
3. `Extension settings` 的总条数包含其他扩展，且不等于 LocalOTP 账号数。两台都显示 7 条也不能证明它们是相同的 7 条。LocalOTP 使用 `acc:`、`cat:`、`tomb:`、`ctomb:` 等键。
4. 在 Sync Node Browser 中展开 `Extension settings`，核对 `extension_id` 是否为插件只读检查显示的运行时 ID，以及 `key` 是否有 `acc:` 前缀。只记录 ID 和各类键的数量；`value` 可能包含账号密码与 OTP 密钥，不要把完整节点或整份同步数据发到问题反馈中。
5. A 的插件缓存有记录，而同步节点没有对应 ID/键：尚无证据表明账号已进入云端传输。A 的节点存在、B 的节点没有：继续排查浏览器传输。B 的节点已有相同 ID 的账号键、插件缓存却为零：检查是否处于同一个浏览器个人资料及实际运行时 ID，再排查扩展存储层。

若 Mac 显示 `Configuring data types` / `cryptographer error`，需按具体数据类型判断。密码和自动填充报错、Extension settings 仍为 Running 时，不能直接认定该加密错误就是 LocalOTP 未收到的原因。先完成上述 ID/键归属检查，再决定是否处理浏览器账号或加密状态；不要把重置整个云同步、卸载扩展当作首个排错步骤。

当前源码把反馈统一为“本机缓存合并完成 / 未确认云端传输”。反复点击只会再次读写当前缓存，不能强制浏览器立即上传或下载。

## 同步节点属于旧 ID 时的一次性迁移

1. 在源电脑找到**实际拥有账号的旧插件**，从设置导出 JSON 备份，并确认账号条数正确。
2. 加载固定 ID 的新版。在其“同步诊断 → 只读检查”中确认运行时 ID 为 `mjpifhendkddjgmoheglnfciammaipji`，再在新版中导入源端备份。
3. 只在源端导入；目标端保持空库，使用相同固定 ID。两端开启插件同步后，以目标端自动出现账号、反向编辑能返回源端为验收依据。

迁移完成前保留旧插件及备份。不要把目标插件改回旧 ID，也不要重新生成公钥。若在扩展管理页同时看到多个 LocalOTP，必须核对有账号的那个实例，而不只是核对新安装的空实例。

## 同步范围与已验证边界

同步账号、分类及删除记录。管理密码、外观、短时免密设置和免密授权不上云；临时验证码输入也不参与同步。

账号密码与 OTP 密钥在本项目中没有额外端到端加密。已验证真实扩展后台和 `storage.sync`、多设备合并模型、错误恢复与重开加载；尚未使用两台登录同一账号的真实设备完成云端传输验收。`tools/sync-isolation-test.mjs` 用两个同 ID 的真实 Edge 配置、显式关闭云同步，检查“A 缓存写入 5 条、B 仍为空”不会被当作跨设备成功；它不验证微软云端传输。

## acc 记录多了，要清理吗？

`acc:` 是账号记录，不是临时日志；正常情况下每个账号对应一条。旧 ID 迁移到固定 ID 后，浏览器同步节点中可能同时保留两个 ID 的账号记录，且页面总条数还可能包含其他扩展。应按 `extension_id` 分开计数，不能仅凭总数判断重复。

- 新版插件账号列表完整、没有重复，且没有容量错误时，无需为了减少计数而清理。不同扩展 ID 的记录属于各自的存储空间，不会被新版自动合并，也不共用新版的单个扩展配额。
- 如果新版列表中确有不需要的测试账号或重复账号，先备份，再从插件界面删除；开启同步时会用删除记录通知其他设备。不要在 Sync Node Browser 或开发者工具中直接批量删除 `acc:`。
- `tomb:` / `ctomb:` 是防止离线设备把已删除账号、分类重新带回来的删除记录，不是可随意移除的垃圾。
- 不再使用的旧 ID 副本可在新库、备份及双向同步都确认完整后单独整理；含真实密码和密钥的多余副本也需要妥善处理。关闭插件同步不会自动清除已写入的同步数据，不要把卸载或清空本机当作云端数据已彻底删除的证明。

2026-11-06 用户反馈：完成源端旧 ID 到固定 ID 的迁移后，Windows / macOS Edge 已能收到账号。这是用户环境的实际反馈；自动化测试仍限于隔离浏览器和模拟传输，尚未独立验收全部跨设备更新、删除及离线恢复场景。
